# WDMCH USB Rescue Boot Guide

## The loader reads fixed filenames from the ROOT of the stick

The vendor U-Boot rescue loader does **not** search directories. It reads
**fixed filenames from the root of the FAT32 filesystem**:

```text
sata.uImage
rescue.sata.dtb
rescue.root.sata.cpio.gz_pad.img
```

There is **no `boot/` subdirectory**. Placing the artifacts in `/boot/` on the
stick is the single most common way to get an unbootable rescue stick — the
loader looks for `/sata.uImage` and never finds it.

## Required stick contents

The complete FAT32 stick, as produced by `image/package-rescue.sh`:

```text
/mnt/stick/                       <- FAT32 root, MBR, single partition
├── sata.uImage                      patched ARM64 Image + 512 KiB zero padding
├── rescue.sata.dtb                  WDMCH device tree blob
├── rescue.root.sata.cpio.gz_pad.img exactly 4194304 bytes
├── SHA256SUMS                       checksums of the three boot files
├── manifest.json                    build metadata
├── README.txt                       instructions, generated by the build
└── apks/                            the only subdirectory
    ├── main/                        Alpine main packages (offline install)
    └── community/                   Alpine community packages
```

`apks/` is the only subdirectory that is allowed to exist.

## Artifact contract

| Artifact | Requirement |
|---|---|
| `sata.uImage` | Raw patched ARM64 `Image` + 512 KiB of zero padding. **Not** a U-Boot `mkimage` or FIT container. Never gzip the `Image`. |
| `rescue.sata.dtb` | Device tree blob for the WDMCH board. |
| `rescue.root.sata.cpio.gz_pad.img` | Gzip'd `newc` cpio, zero-padded to **exactly 4194304 bytes**. The loader reads that fixed size unconditionally, so a short or oversized file fails. |

### Kernel header patch

`sata.uImage` begins with an `Image` whose ARM64 header has been patched:

```text
code0       = 0x91005A4D   (offset 0)
text_offset = 0x200000     (offset 8)
pe_offset   = 0x40         (offset 60)
```

## Preparing the stick

The stick must be **FAT32, MBR, single partition**, and the build tree must sit
in its **root** — the vendor loader reads fixed filenames from there, so a
`boot/` subdirectory cannot boot.

Do it the verified way. It partitions, copies, and then proves the result,
which is what catches a truncated write before you open the box:

```bash
tools/prepare-usb.sh --device /dev/sdX
```

`--device` is destructive and refuses a device that is not flagged removable
unless you also pass `--force-internal`. Confirm the candidate with
`lsblk -o NAME,SIZE,TYPE,MODEL,TRAN` first.

Already have a stick mounted? Verify it in place; this is read-only and is the
same check the script runs after copying:

```bash
tools/prepare-usb.sh --image /mnt/stick
```

It confirms all six required files are present and non-empty, that
`sata.uImage` still validates as an ARM64 Image, that the initramfs is still
exactly 4194304 bytes, that `SHA256SUMS` matches, that there is no `boot/`
directory, and that the offline repository has not lost packages.

By hand, if you prefer — verify the outcome yourself, it is the whole point:

```bash
mount /dev/sdX1 /mnt/stick
cp -a build/usb-tree-root/. /mnt/stick/     # note the /. - copies hidden files too
sync
cd /mnt/stick
sha256sum -c SHA256SUMS                      # all three artifacts must be OK
stat -c '%s' rescue.root.sata.cpio.gz_pad.img   # must be 4194304
ls -d boot 2>/dev/null && echo "WRONG LAYOUT" || echo "root-level layout OK"
```

## Booting

The vendor U-Boot **cannot boot from the internal SATA disk**. It only reads
boot files from the FAT32 USB stick, either because the reset button is held at
power-on, or automatically when no factory partition is found.

1. Power off the WD My Cloud Home.
2. Insert the stick into the front USB port.
3. Press and **hold the reset button** while powering on.
4. U-Boot `boot_rescue_from_usb` loads `sata.uImage`, `rescue.sata.dtb` and
   `rescue.root.sata.cpio.gz_pad.img` from the stick root into RAM. The
   initramfs is staged at physical `0x02200000`, 4 MiB.
5. The rescue initramfs boots, mounts the stick, brings up `eth0` via DHCP and
   starts dropbear (public-key only, port 22).
6. The rescue init looks for a filesystem labelled `wdmch-root` on the internal
   disk. If it holds a valid system, it is mounted and `switch_root` is used to
   continue into the installed Alpine — the box boots normally with the stick
   still plugged in.
7. If an installed system is found, the rescue init prints a **20-second
   countdown** on the serial console before handing over. Press `ENTER` on the
   console during that window to keep the rescue shell instead.

## After the first boot: verify the install

The build cannot check the parts that only exist on real hardware — the
`switch_root` handover, the preserved partition table, DHCP and SSH. The
installer therefore copies a health check onto the target:

```sh
verify-install
```

Run it over SSH (or from the serial console) once the box has come up. It
checks, and exits non-zero if any fail:

- an init is present and executable, and PID 1 is an init
- `/` really is the btrfs filesystem labelled `wdmch-root`, spanning p20 and p21
- `/` is mounted read-write
- the internal disk still exposes at least 20 partitions — i.e. the factory
  GPT was **not** rewritten
- `/boot/Image` is present, so `boot-full-alpine` can kexec
- the offline install completed: `busybox`, `openrc`, `openrc-init`,
  `dropbear`, `ifupdown-ng` and `mdev-conf` are all in the apk database
- `eth0` has an address and dropbear is running

The same script runs offline against a mounted target root, which skips the
host-relative checks:

```sh
verify-install /mnt/target
```

If it reports `FAIL`, the specific failing line names what broke.

## SSH access

```bash
ssh root@<ip>
```

- Dropbear listens on **port 22**.
- **Public-key authentication only.** There is no root password and password
  authentication is refused.
- The operator's public key is supplied at build time via the
  `WDMCH_SSH_AUTHORIZED_KEY` secret. No private key ever ships in the repo or
  in any artifact.

## Forcing the rescue shell instead of the installed system

Create an empty file named `norescue` in the **root** of the USB stick:

```bash
touch /mnt/stick/norescue
```

The rescue init then skips the `wdmch-root` handoff and drops to a serial / SSH
rescue shell instead of switching into the installed system. Remove the file to
restore normal handoff behaviour.

## Optional: booting without the stick

On the installed system, `/usr/local/sbin/boot-full-alpine` prepares a `kexec`
into the kernel stored in the system's on-disk `/boot` directory. `kexec -e`
then reboots into it without the USB stick present.

## Safety

- **DO NOT** boot the GOLD partition — it is a factory-reset appliance, not a
  safe fallback.
- **DO NOT** write the A/B/GOLD firmware slots.
- **DO** back up the existing WDMCH firmware table (partition p1) before any
  flashing work.
- Building the rescue stick is **read-only** with respect to the NAS.
- `install-alpine` does write to the disk, but it only writes the existing p20
  and requires explicit confirmation. See [INSTALL.md](INSTALL.md).
